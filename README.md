# AI Chatbot

A local AI chatbot built with Python, Streamlit, and Ollama. The project demonstrates agent orchestration, tool usage, context management, memory, prompt engineering, and guardrails without relying on agent frameworks such as LangChain or CrewAI.

## Overview

The chatbot processes user messages through a lightweight agent architecture composed of an Orchestrator, a Math Agent, and a Writer Agent.

Mathematical operations are executed exclusively by application tools. The language model is never responsible for calculating mathematical results.

The Writer Agent receives the authoritative result generated by the mathematical workflow and converts it into a natural-language response.

The application also maintains session-based memory so that mathematical operations can reference previous results.

### Example

```text
User: 5 + 4
Bot: The result is 9.

User: divide 2
Bot: The result is 4.5.
```

In the second interaction, the Math Agent retrieves `9` from memory and applies the division operation through the mathematical tool.

## Architecture

The application follows a simple layered architecture that separates responsibilities between mathematical processing, orchestration, language generation, and memory.

```text

                         │    Streamlit     │
                         │      app.py      │
                         └────────┬─────────┘
                                  │
                                  ▼
                         ┌──────────────────┐
                         │   Orchestrator   │
                         │   Coordinates    │
                         └───────┬──────────┘
                                 │
                    ┌────────────┴────────────┐
                    │                         │
                    ▼                         ▼
            ┌───────────────┐         ┌────────────────┐
            │   Math Agent  │         │  Writer Agent  │
            │               │         │                │
            │ Parse context │         │ Natural        │
            │ Call tools    │         │ language       │
            │ Store result  │         │ response       │
            └───────┬───────┘         └───────┬────────┘
                    │                         │
                    ▼                         ▼
            ┌───────────────┐         ┌────────────────┐
            │ Mathematical  │         │ LLM Provider   │
            │    Tools      │         │   Abstraction  │
            └───────────────┘         └───────┬────────┘

                                       │ llama3.2:3b  │
                                       └──────────────┘

                    ┌──────────────────┐
                    │      Memory      │
                    │ Latest math      │
                    │     result       │
                    └──────────────────┘
```

## Agents

### Orchestrator

The Orchestrator is responsible for coordinating the application workflow.

It does not:

* Parse mathematical expressions
* Perform mathematical calculations
* Access mathematical tools directly
* Interpret mathematical context
* Modify mathematical results

Its responsibility is to pass the user message through the appropriate workflow and coordinate the Math Agent and Writer Agent.

### Math Agent

The Math Agent owns the mathematical workflow.

Its responsibilities include:

* Detecting mathematical expressions
* Normalizing mathematical expressions
* Tokenizing expressions
* Handling operator precedence
* Parsing contextual mathematical operations
* Retrieving previous results from memory
* Calling mathematical tools
* Storing new results in memory
* Returning a structured mathematical result

The Math Agent is the only component responsible for mathematical interpretation and execution.

#### Source of truth

Mathematical results come exclusively from application tools.

The language model does not calculate the result.

For example:

```text
User: 5 + 4

Math Agent
    │
    ├── Parse expression
    │
    ├── Call add(5, 4)
    │
    └── Result = 9
```

The value `9` is then passed to the Writer Agent as an authoritative result.

### Writer Agent

The Writer Agent is responsible only for communicating results naturally to the user.

When a mathematical result is available, the Writer Agent:

* Receives the authoritative result
* Generates a short natural-language response
* Uses the user's language
* Does not perform mathematical calculations
* Does not reinterpret the mathematical operation
* Does not modify the result

The application validates the generated response before replacing the result placeholder with the authoritative value.

If the generated response violates the guardrails, the application falls back to a deterministic response.

## Mathematical Tools

Mathematical calculations are implemented as application-level tools.

Available operations:

```text
add()
subtract()
multiply()
divide()
```

The Math Agent selects the appropriate tool according to the parsed operation.

For example:

```text
5 + 4
```

is processed as:

```text
add(5, 4) → 9
```

For contextual operations:

```text
5 + 4
divide 2
```

the workflow becomes:

```text
5 + 4
    ↓
add(5, 4)
    ↓
9
    ↓
Memory
    ↓
divide(9, 2)
    ↓
4.5
```

Division by zero and unsupported operations are handled by the mathematical tool layer.

## Memory

The application uses a `Memory` class to store the latest mathematical result.

Memory is instantiated per Streamlit session and stored in `st.session_state`.

This prevents mathematical results from being shared globally between independent user sessions.

Example:

```text
User: 10 + 5
Bot: The result is 15.

User: divide 3
Bot: The result is 5.
```

The second operation uses the previous result stored in the current session.

The memory API is intentionally small:

```python
memory.save_result(result)
memory.get_last_result()
```

## LLM Provider Architecture

The project separates the application from the concrete LLM provider through a provider abstraction.

```text
Application
     │
     ▼
Provider Factory
     │
     ▼
Base Provider
     │
     ▼
Ollama Provider
     │
     ▼
Ollama
```

The current local provider uses Ollama with:

```text
llama3.2:3b
```

This abstraction allows the application logic to remain independent from the specific LLM implementation.

The agents interact with the provider interface rather than directly coupling their logic to Ollama.

## Installation

Clone the repository:

```bash
git clone <repository-url>
cd chatbot-project
```

Create a virtual environment:

```bash
python -m venv .venv
```

Activate it on Windows PowerShell:

```powershell
.venv\Scripts\Activate.ps1
```

Install the Python dependencies:

```bash
pip install -r requirements.txt
```

Make sure Ollama is running and the required model is available:


## Design Principles

The implementation follows several important principles.

### Separation of responsibilities

Each component has a defined responsibility.

The Orchestrator coordinates.

The Math Agent interprets and executes mathematical requests.

The mathematical tools perform calculations.

The Writer Agent communicates results.

Memory stores contextual state.

### Deterministic mathematical execution

Mathematical calculations are deterministic application logic.

The LLM is not trusted as a mathematical source of truth.

### Explicit context handling

Contextual requests such as:

```text
divide 2
```

are resolved using the previous mathematical result stored in session memory.

### Provider abstraction

The application does not directly couple agent logic to a specific LLM implementation.

### Guardrails

The Writer Agent is constrained so that generated text cannot replace the authoritative mathematical result with a value produced by the model.
