# AI Chatbot

A local AI chatbot built with Python, Streamlit, and Ollama. The project demonstrates agent orchestration, tool usage, context management, memory, prompt engineering, guardrails, and LLM provider abstraction without relying on agent frameworks such as LangChain or CrewAI.

## Overview

The chatbot processes user messages through a lightweight agent architecture composed of an Orchestrator, a Math Agent, and a Writer Agent.

Mathematical operations are executed exclusively by application tools. The language model is never responsible for calculating mathematical results.

The Writer Agent receives the authoritative result generated by the mathematical workflow and converts it into a natural-language response.

The application maintains two complementary forms of session state:

- Streamlit conversation history stores previous user and assistant messages.
- The `Memory` service stores the latest authoritative mathematical result for contextual mathematical operations.

### Example

```text
User: 5 + 4

Bot: The result is 9.

User: divide 2

Bot: The result is 4.5.
```

In the second interaction, the Math Agent retrieves `9` from memory and applies the division operation through the mathematical tool.

## Agents

### Orchestrator

The Orchestrator is responsible for coordinating the application workflow.

It does not:

- Parse mathematical expressions
- Perform mathematical calculations
- Access mathematical tools directly
- Interpret mathematical context
- Modify mathematical results

Its responsibility is to pass the user message through the appropriate workflow and coordinate the Math Agent and Writer Agent.

### Math Agent

The Math Agent owns the mathematical workflow.

Its responsibilities include:

- Detecting mathematical expressions
- Normalizing mathematical expressions
- Extracting supported mathematical expressions
- Parsing contextual mathematical operations
- Retrieving previous results from memory
- Calling mathematical tools
- Storing new results in memory
- Returning a structured mathematical result

The Math Agent is responsible for mathematical interpretation and for coordinating the execution of mathematical requests through deterministic application tools. The tools perform the calculations and provide the authoritative results.

The Math Agent has an explicit agent prompt that defines its responsibilities and guardrails. The prompt establishes that:

- Mathematical operations must be executed through application tools.
- Tool results are the authoritative source of truth.
- The Math Agent must not calculate through language-model reasoning.
- The Math Agent must not generate the final conversational response.
- The Math Agent must return structured mathematical results to the Orchestrator.

The prompt defines the Math Agent contract and its guardrails. The agent can use an LLM as an interpretation fallback. Structured responses are validated before execution, and mathematical calculations are always performed by deterministic application tools.

### Writer Agent

The Writer Agent is responsible only for communicating results naturally to the user.

When a mathematical result is available, the Writer Agent:

- Receives the authoritative result
- Generates a short natural-language response
- Uses the user's language
- Does not perform mathematical calculations
- Does not reinterpret the mathematical operation
- Does not modify the result

The Writer Agent uses dedicated prompts with explicit guardrails.

The application validates the generated response before replacing the result placeholder with the authoritative value.

If the generated response violates the guardrails, the application falls back to a deterministic response.

## Mathematical Tools

Mathematical calculations are implemented as application-level tools.

Available operations:

```python
add()
subtract()
multiply()
divide()
```

The Math Agent selects the appropriate tool according to the parsed operation.

For example:

```text
5 + 4
```

is processed as:

```text
add(5, 4) -> 9
```

For contextual operations:

```text
5 + 4

divide 2
```

the workflow becomes:

```text
5 + 4
    |
    v
add(5, 4)
    |
    v
9
    |
    v
Memory
    |
    v
divide(9, 2)
    |
    v
4.5
```

Division by zero and unsupported operations are handled by the mathematical tool and parsing layers.

## Mathematical Parsing

The application prioritizes deterministic parsing for supported mathematical expressions and contextual operations. When deterministic interpretation is insufficient, the Math Agent may use an LLM to interpret the request. For expression interpretations, the agent validates the expression structure and checks whether it is grounded in the user message before execution. All mathematical calculations are performed by application tools.

### Expression Extractor

`core/expression_extractor.py` is responsible for:

- Normalizing mathematical vocabulary
- Converting supported number words into numeric values
- Converting supported mathematical words into operators
- Extracting complete mathematical expressions from natural-language messages
- Detecting malformed mathematical expressions

The parser supports common mathematical vocabulary in English, Portuguese, and Spanish.

Examples:

```text
How much is 5 + 4?       -> 5+4

Quanto é 5 + 4?          -> 5+4

¿Cuánto es 5 + 4?        -> 5+4

five plus four           -> 5+4

cinco más cuatro         -> 5+4

dos más cuatro           -> 2+4
```

### Intent Parser

`core/intent_parser.py` handles contextual mathematical operations such as:

```text
divide 2

subtract 3

add 5

multiply 2
```

and Portuguese equivalents such as:

```text
dividido por 2

menos 3

mais 5

multiplica por 2
```

These operations use the latest result stored in session memory as the first operand.

The parser also includes Spanish contextual number-word handling, such as:

```text
dividir por siete
```

The parsing logic is deterministic and does not rely on an LLM to infer the mathematical operation when a supported pattern can be parsed directly.

## Memory

The application uses two complementary forms of session state.

### Conversation history

Streamlit stores the conversation history in:

```python
st.session_state.messages
```

This contains the previous user and assistant messages displayed by the chat interface.

The history is scoped to the current Streamlit session and is preserved during the active conversation.

### Mathematical memory

The `Memory` class stores the latest authoritative mathematical result.

Memory is instantiated per Streamlit session and stored in `st.session_state`.

This prevents mathematical results from being shared globally between independent user sessions.

Example:

```text
User: 10 + 5

Bot: The result is 15.

User: divide 3

Bot: The result is 5.
```

The second operation uses the previous result stored in the current session.

The memory API is intentionally small:

```python
memory.save_result(result)

memory.get_last_result()
```

The separation is intentional:

- Conversation history provides conversational state for the interface.
- Mathematical memory provides the specific numerical context required for follow-up calculations.

## LLM Provider Architecture

The project separates the application from concrete LLM implementations through a provider abstraction.

```text
Application
     |
     v
Provider Factory
     |
     v
Fallback Provider
     |
     +--> Ollama Provider
     |
     +--> Gemini Provider
     |
     +--> OpenAI Provider
```

The provider factory configures the fallback order through the `CHATBOT_PROVIDERS` environment variable. By default, only the local `ollama` provider is enabled. Cloud providers such as Gemini and OpenAI must be explicitly included in `CHATBOT_PROVIDERS`.

The default models configured by the application are:

- Ollama: `llama3.2:3b`
- Gemini: `gemini-3.8-flash`
- OpenAI: `gpt-5.6-terra`

The fallback provider tries each configured provider in order and returns the first non-empty response. If all providers fail, it raises a `ProviderFallbackError`.

A configured cloud provider with a missing required API key raises `ProviderConfigurationError`, allowing the fallback chain to try the next configured provider. Invalid global `CHATBOT_PROVIDERS` configuration (empty lists, duplicate names, or unsupported providers) fails immediately with `ValueError`. Only explicitly classified operational errors and provider-specific configuration errors allow fallback; unexpected programming errors propagate. Fallback diagnostics and logs include the provider name and exception type, not raw exception messages or credentials.

Provider-related modules are located under:

```text
llm/
    provider_factory.py
    providers/
        base_provider.py
        errors.py
        fallback_provider.py
        ollama_provider.py
        gemini_provider.py
        openai_provider.py
```

### Provider Configuration

| Variable | Purpose | Default |
|---|---|---|
| `CHATBOT_PROVIDERS` | Comma-separated provider order | `ollama` |
| `OLLAMA_MODEL` | Ollama model identifier | `llama3.2:3b` |
| `GEMINI_API_KEY` | Gemini API key | Required when Gemini is used |
| `GEMINI_MODEL` | Gemini model identifier | `gemini-3.8-flash` |
| `OPENAI_API_KEY` | OpenAI API key | Required when OpenAI is used |
| `OPENAI_MODEL` | OpenAI model identifier | `gpt-5.6-terra` |

Ollama runs locally. Gemini and OpenAI require valid API credentials when they are included in the provider chain.

For example, to use Gemini before OpenAI without Ollama, configure:

```powershell
$env:CHATBOT_PROVIDERS = "gemini,openai"
$env:GEMINI_API_KEY = "your-gemini-api-key"
$env:OPENAI_API_KEY = "your-openai-api-key"
```

These commands set environment variables for the current PowerShell session only. Use secure secret management for persistent or production deployments; do not commit API keys to the repository.

If a provider fails or returns an empty response, the fallback mechanism attempts the next configured provider.

## Requirements

Before running the application, make sure the following are installed:

- Python 3.14.4 (validated; other versions have not been verified)
- Ollama, if using the local provider
- Git

Install the Ollama application separately from [the official download page](https://ollama.com/download). The `ollama` entry in `requirements.txt` is the Python client library; it does not install the Ollama application.

The project uses the following default Ollama model:

```text
llama3.2:3b
```

For Windows systems using an AMD GPU through Vulkan, the application can be configured with:

```powershell
setx OLLAMA_VULKAN "1"
setx GGML_VK_VISIBLE_DEVICES "0"
setx HIP_VISIBLE_DEVICES "-1"
```

After setting these variables, restart the Ollama process and open a new terminal session so the environment variables are applied to newly started processes.

The exact Vulkan device index may vary depending on the GPUs detected by the system.

For Gemini and OpenAI, configure the corresponding API key environment variables before using those providers.

## Design Principles

### Separation of responsibilities

Each component has a defined responsibility.

The Orchestrator coordinates.

The Math Agent interprets mathematical requests and coordinates their execution through application tools.

The mathematical tools perform calculations.

The Writer Agent communicates results.

Memory stores contextual state.

### Deterministic mathematical execution

Mathematical calculations are deterministic application logic.

The LLM is not trusted as a mathematical source of truth.

### Explicit context handling

Contextual requests such as:

```text
divide 2
```

are resolved using the previous mathematical result stored in session memory.

### Provider abstraction

The application does not directly couple agent logic to a specific LLM implementation. Providers are selected through configuration and are invoked through the fallback mechanism.

### Guardrails

The Writer Agent is constrained so that generated text cannot replace the authoritative mathematical result with a value produced by the model.

### Testable architecture

Core mathematical logic, agents, services, and provider components are separated from the Streamlit presentation layer, making the main application behavior independently testable.
