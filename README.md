# AI Chatbot

A local AI chatbot built with Python, Streamlit, and Ollama. The project demonstrates agent orchestration, tool usage, context management, memory, prompt engineering, guardrails, and LLM provider abstraction without relying on agent frameworks such as LangChain or CrewAI.

## Overview

The chatbot processes user messages through a lightweight agent architecture composed of an Orchestrator, a Math Agent, and a Writer Agent.

Mathematical operations are executed exclusively by application tools. The language model is never responsible for calculating mathematical results.

The Writer Agent receives the authoritative result generated by the mathematical workflow and converts it into a natural-language response.

The application maintains two complementary forms of session state:

* Streamlit conversation history stores previous user and assistant messages.
* The `Memory` service stores the latest authoritative mathematical result for contextual mathematical operations.

### Example

```text
User: 5 + 4

Bot: The result is 9.

User: divide 2

Bot: The result is 4.5.
```

In the second interaction, the Math Agent retrieves `9` from memory and applies the division operation through the mathematical tool.

## Architecture

The application follows a simple layered architecture that separates responsibilities between mathematical processing, orchestration, language generation, and memory.

                       |                         |
                       v                         v
               +----------------+       +----------------+
               |   Math Agent   |       |  Writer Agent  |
               |                |       |                |
               | Parse context  |       | Natural        |
               | Parse math     |       | language       |
               | Call tools     |       | response       |
               | Store result   |       | guardrails     |

## Agents

### Orchestrator

The Orchestrator is responsible for coordinating the application workflow.

It does not:

* Parse mathematical expressions
* Perform mathematical calculations
* Access mathematical tools directly
* Interpret mathematical context
* Modify mathematical results

Its responsibility is to pass the user message through the appropriate workflow and coordinate the Math Agent and Writer Agent.

### Math Agent

The Math Agent owns the mathematical workflow.

Its responsibilities include:

* Detecting mathematical expressions
* Normalizing mathematical expressions
* Tokenizing expressions
* Evaluating expressions with operator precedence
* Parsing contextual mathematical operations
* Retrieving previous results from memory
* Calling mathematical tools
* Storing new results in memory
* Returning a structured mathematical result

The Math Agent is the only component responsible for mathematical interpretation and execution.

The Math Agent has an explicit agent prompt that defines its responsibilities and guardrails. The prompt establishes that:

* Mathematical operations must be executed through application tools.
* Tool results are the authoritative source of truth.
* The Math Agent must not calculate through language-model reasoning.
* The Math Agent must not generate the final conversational response.
* The Math Agent must return structured mathematical results to the orchestrator.

The Math Agent prompt is used as an explicit agent contract. Mathematical execution remains deterministic and does not depend on an LLM.

### Writer Agent

The Writer Agent is responsible only for communicating results naturally to the user.

When a mathematical result is available, the Writer Agent:

* Receives the authoritative result
* Generates a short natural-language response
* Uses the user's language
* Does not perform mathematical calculations
* Does not reinterpret the mathematical operation
* Does not modify the result

The Writer Agent uses dedicated prompts with explicit guardrails.

The application validates the generated response before replacing the result placeholder with the authoritative value.

If the generated response violates the guardrails, the application falls back to a deterministic response.

## Mathematical Tools

Mathematical calculations are implemented as application-level tools.

Available operations:

```text
add()

subtract()

multiply()

divide()
```

The Math Agent selects the appropriate tool according to the parsed operation.

For example:

```text
5 + 4
```

is processed as:

```text
add(5, 4) -> 9
```

For contextual operations:

```text
5 + 4

divide 2
```

the workflow becomes:

```text
5 + 4
    |
    v
add(5, 4)
    |
    v
9
    |
    v
Memory
    |
    v
divide(9, 2)
    |
    v
4.5
```

Division by zero and unsupported operations are handled by the mathematical tool layer.

## Mathematical Parsing

The application uses deterministic parsing components instead of delegating mathematical interpretation to the language model.

### Expression Extractor

`core/expression_extractor.py` is responsible for:

* Normalizing mathematical vocabulary
* Converting supported number words into numeric values
* Converting mathematical words into operators
* Extracting complete mathematical expressions from natural-language messages
* Detecting malformed mathematical expressions
* Detecting contextual shorthand operations

The parser supports common mathematical vocabulary in English, Portuguese, and Spanish.

Examples:

```text
How much is 5 + 4?       -> 5+4

Quanto é 5 + 4?          -> 5+4

¿Cuánto es 5 + 4?        -> 5+4

five plus four            -> 5+4

cinco más cuatro          -> 5+4
```

### Intent Parser

`core/intent_parser.py` handles contextual mathematical operations such as:

```text
divide 2

subtract 3

add 5

multiply 2
```

and Portuguese equivalents such as:

```text
dividido por 2

menos 3

mais 5

multiplica por 2
```

These operations use the latest result stored in session memory as the first operand.

The parsing logic is deterministic and does not rely on an LLM to infer the mathematical operation.

## Memory

The application uses two complementary forms of session state.

### Conversation history

Streamlit stores the conversation history in:

```text
st.session_state.messages
```

This contains the previous user and assistant messages displayed by the chat interface.

The history is scoped to the current Streamlit session and is preserved during the active conversation.

### Mathematical memory

The `Memory` class stores the latest authoritative mathematical result.

Memory is instantiated per Streamlit session and stored in `st.session_state`.

This prevents mathematical results from being shared globally between independent user sessions.

Example:

```text
User: 10 + 5

Bot: The result is 15.

User: divide 3

Bot: The result is 5.
```

The second operation uses the previous result stored in the current session.

The memory API is intentionally small:

```python
memory.save_result(result)

memory.get_last_result()
```

The separation is intentional:

* Conversation history provides conversational state for the interface.
* Mathematical memory provides the specific numerical context required for follow-up calculations.

## LLM Provider Architecture

The project separates the application from concrete LLM implementations through a provider abstraction.

```text
Application
     |
     v
Provider Factory
     |
     v
Base Provider
     |
     +------------------+
     |                  |
     v                  v
Ollama Provider     Other Providers
     |              (implemented separately)
     v
  Ollama
     |
     v
llama3.2:3b
```

The local application uses Ollama with:

```text
llama3.2:3b
```

Provider-related modules are located under:

```text
llm/

    provider_factory.py

    providers/

        base_provider.py
        ollama_provider.py
        openai_provider.py
        claude_provider.py
```

The active application provider is Ollama. `OpenAIProvider` is implemented as an additional provider implementation, while `claude_provider.py` is reserved for future provider support.

## Design Principles

### Separation of responsibilities

Each component has a defined responsibility.

The Orchestrator coordinates.

The Math Agent interprets and executes mathematical requests.

The mathematical tools perform calculations.

The Writer Agent communicates results.

Memory stores contextual state.

### Deterministic mathematical execution

Mathematical calculations are deterministic application logic.

The LLM is not trusted as a mathematical source of truth.

### Explicit context handling

Contextual requests such as:

```text
divide 2
```

are resolved using the previous mathematical result stored in session memory.

### Provider abstraction

The application does not directly couple agent logic to a specific LLM implementation.

### Guardrails

The Writer Agent is constrained so that generated text cannot replace the authoritative mathematical result with a value produced by the model.

### Testable architecture

Core mathematical logic, agents, services, and provider components are separated from the Streamlit presentation layer, making the main application behavior independently testable.
